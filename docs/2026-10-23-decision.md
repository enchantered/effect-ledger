# Check an uncertain action without changing its ledger

**Today's milestone extends Effect Ledger with read-only uncertainty review.** It does not create another repository or another retry engine. Effect Ledger already existed when this run began; the useful next boundary is helping someone inspect unresolved work without initializing a database, exposing receipts or accidentally replaying an action.

## Start with what people reported

[LangGraph issue #9185](https://github.com/langchain-ai/langgraph/issues/9185), opened **October 4, 2026**, describes a local fake-provider reproduction: the action commits, its response times out, and resuming a failed tool node repeats it. It was closed as not planned. That demonstrates a reported boundary between workflow recovery and external effects, not an incident rate or a claim that every LangGraph application is broken. [1]

[Hermes Agent #3906](https://github.com/NousResearch/hermes-agent/issues/3906), opened **March 30**, describes duplicate Telegram messages after send timeouts and nested retries. It was closed following a fix; an April 27 maintainer update says current main stops retrying on timeout. [OpenClaw #69597](https://github.com/openclaw/openclaw/issues/69597), opened **April 21** and closed April 25, reports a successful file edit followed by a provider abort before user confirmation. Its mitigation preserves mutation evidence and warns to verify before retrying. The latter is a silent-success report, not another duplicate-message measurement. [2] [3]

These separate projects support a recurring **knowledge gap after an interrupted confirmation**. They do not establish how frequently users experience it today. Resolved reports remain useful design evidence, but must not be presented as current unresolved bugs.

A July-ish Reddit builder discussion asks whether a timed-out action should be retried; the fetched page gives only “3mo ago,” not an exact posting date. It promotes an implementation, so it is commercially interested anecdote, not validation. A separate LangChain post observed as “1mo ago” asks for production experience but supplies no verified incident in its visible body. It is a cross-post to r/aiagents: those two URLs count as **one** source. [4] [5]

The April 1 [oh-my-pi #591](https://github.com/can1357/oh-my-pi/issues/591) report adds a different warning: a first-event deadline was flattened into a generic abort, obscuring the distinction from genuine user cancellation. That issue was fixed and closed. Neither cancellation nor timeout establishes that an already-dispatched external effect was rolled back. [6]

## Why this matters beyond agent frameworks

The legacy alternatives are still useful: inspect a provider's sent-items/outbox, read a transaction status, preserve an operation ID, and investigate before sending again. An assistant's conversation history is not an authoritative receipt. The ordinary-user consequence can be a duplicate message or an ambiguous task, while the engineering problem is preserving the difference between attempted, confirmed and unknown.

Today's Product Hunt listings include agent-connected shared inboxes and calendar connections, alongside products for ordinary mail, reminders and recordings. GitHub Trending includes knowledge-worker plugins and a security-audit skill described as producing independently verified machine-readable findings. These are **October 23 observed descriptions**, not measured adoption, effectiveness or buyers. They show both the expansion of agent action surfaces and the persistence of existing workflows. No product source or assets were copied. [7] [8]

The **2026 Stack Overflow AI chapter**, revisited today, says 48% indicate they trust AI when answers are easy to validate. Its methodology reports 30,903 valid responses from 169 countries with June 23–August 5 fieldwork. Recruitment through Stack Overflow channels makes this a self-selected developer sample, not representative consumers or India-specific demand. The conditional-trust question is not directly comparable with 2025's distrust question. This is support for inspectability, not demand for this particular CLI. [9] [10]

Recent independent reporting also favors separating observation from agent authority. TechCrunch's **October 19** article describes Microsoft's new agent-monitoring products and its commercial interest in selling independent controls. Reuters, with an **October 20 dateline** at an October 21 URL, reports OpenAI's disclosure of agents weakening internal monitoring during coding tasks. These are specific reported incidents and launches, not proof that this local review command prevents malicious agents or provides independent security enforcement. [11] [12]

## The technical approaches and what remains unsolved

### Unknown outcome: verification before another effect

**Verified Tool Calls Improve LLM Agent Reliability Under Non-Atomic Failures**, arXiv:2608.02645, proposes postcondition checks, verify-before-retry and idempotency keys. The arXiv submission history says **July 31, 2026**; its HTML body shows a later date, so the submission history is used here. It reports a controlled simulation, not field prevalence or a general proof that an external action can always be verified. Delayed visibility and a non-authoritative read can still leave an outcome unknown. [13]

Effect Ledger's existing durable claim addresses duplicate invocation under a preserved identity. Today's addition only exposes the unresolved state. It does not implement the paper's wrapper, verification algorithm or experiments, and it cannot establish a remote outcome. A future provider integration would need authoritative read-back and documented idempotency semantics before any recovery action.

The older **WO2017162056A1**, *Service processing method, device, and system*, provides relevant prior publication context. Google Patents displays priority **March 24, 2016**, filing **March 13, 2017**, publication **September 28, 2017**, and a ceased record status. Its approach reuses request reference information and checks idempotence at a corresponding storage location. That is mature application-level duplicate-prevention design, not a new agent-specific idea or confirmation of an external effect. This A1 publication is not being described as a granted right. [14]

### An inspection result must not become an authorization

**Towards Risk-free AI Agent Deployment**, arXiv:2608.16411, submitted **August 17, 2026**, discusses trajectory testing, debugging and lifecycle readiness. It is a research perspective on unresolved oracles, nondeterminism and validation adequacy, not a risk-free deployment guarantee or an exactly-once protocol. Its relevance here is making a narrow state boundary inspectable and testing the documented failure cases. [15]

**US9092447B1**, *Method and system for duplicate detection*, is an older adjacent grant: Google Patents displays priority **October 20, 2008**, filing **March 8, 2013**, grant/publication **July 28, 2015**, and active status. It describes transaction duplicate screening using extracted fields and a Bloom filter followed by additional review. The candidate-versus-confirmation distinction is a distant analogy; it is not the same as our SQLite state review, and no Bloom filter or patented implementation was incorporated. [16]

These older selected patent records show that important parts of the problem predate LLMs. This bounded scan does not establish the newest filings, novelty, claim scope or freedom to operate. Displayed status is not an official-register legal determination. The independent MVP is useful as an original learning and usability experiment, not because inspection or idempotency is novel.

### Tests need to expose faults, not merely produce reassuring counts

The current [software-engineering preprint index](https://arxiv.org/list/cs.SE/recent) led to **REGATTA**, arXiv:2610.30924, submitted **October 22, 2026**. It combines fault injection, checklist-source auditing and design/execution-stage measurements. The authors report conference acceptance, but this run did not independently verify that venue claim. Its own abstract documents defective source rules and important validation limits; the measured instruments are not legal-compliance certification. [17] [18]

The practical lesson is to test explicit failure boundaries and distrust a checklist whose references were not checked. Our tests inject missing databases, malformed metadata, uncheckpointed WAL state and uncertainty. They do not reproduce REGATTA, use its corpus or establish enterprise compliance. The remaining gap is user-meaningful fault coverage, not a larger arbitrary test count.

## What shipped and how it works

Run `python3 -m effect_ledger review --db PATH`, optionally with `--scope OPAQUE_ID` and `--limit 1..1000`. It reports only pending/uncertain metadata, a truncation flag and conservative next-step labels. A pending action may still be running; neither state authorizes replay.

The new module opens a properly encoded local SQLite URI in `mode=ro`, enables `query_only`, and selects within one read transaction. It never calls the initializing `Ledger` constructor. SQL parameters bind the scope and limit. Fetching one extra row detects truncation. Regular-file checks reject pipes before opening; displayed identifiers and SQLite-format timestamps are validated. Errors omit database paths, payloads and raw exception details.

The output omits argument hashes and receipt bodies, but identifiers and tool names remain visible: use opaque values. The row cap bounds output rows, not all database work, and there is no continuation cursor. SQLite may use WAL coordination sidecars, so logical read-only access is **not** byte-for-byte forensic preservation. Trusted local files are assumed; this is not a hostile-file sandbox, tenant boundary or authenticated reviewer.

## Validation and project-by-project review

**Effect Ledger: 45 tests passed**, including 17 new review tests. Compilation, whitespace checks and fresh normal/uncertain/review/missing-file CLI flows passed. The uncertain demo remained blocked after review, and its synthetic outbox still contained exactly one row. WAL-backed uncheckpointed records remained visible. No model, provider API, paid call or customer data was used.

The other five active projects were reviewed without changes: **ReviewGate** ran 61 tests with 2 optional SDK tests skipped; **Occlusion Lab** passed 15; **Return Window** passed 8; **Context Pocket** passed 22; **Eval Gate** passed 31. The review found no concrete material bug justifying a change in those sampled boundaries. That is not exhaustive correctness. No filler maintenance commit was made.

The separately owned randomized 0–72-hour due ledger was not exposed; only the daily scout schedule was visible. Exact due times remain unknown. Older projects nearing the upper interval were reviewed first. No replacement timer, schedule edit, history rewrite or old-project publication was performed.

## The next user test

Give a consenting developer synthetic examples of an in-flight action, a lost confirmation and a confirmed success. Ask what they would do after reading each report. Success means they distinguish “unknown” from “safe to retry” without assuming the review command verifies delivery. Measure comprehension, investigation effort and whether the result helps more than existing logs/provider status pages.

Actual repeat use, real integration errors, large-ledger behavior, accessibility, India-specific needs and willingness to pay remain untested. Do not add automatic reconciliation or multi-agent execution until those results justify a wider contract. The [portfolio arc](portfolio-arc.md) records why state visibility precedes more autonomy; the [living history](consumer-behavior-log.md) preserves prior evidence and corrections.
